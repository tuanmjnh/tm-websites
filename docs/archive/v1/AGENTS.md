# AGENTS.md — TM Websites Monorepo

Guidance for AI coding agents working across the `tm-websites` monorepo.

## Monorepo Architecture

`tm-websites` is a multi-tenant customer storefront & CMS platform powered by Nuxt 4, Nuxt UI v4, Tailwind CSS v4, and MongoDB/Supabase backends.

- **`tm-cms/`**: SPA Customer Administration Suite (`ssr: false`) extending `@tm/nuxt-layer-cms-base`.
- **`tm-web/`**: Universal Public Storefront (`ssr: true`) extending `@tm/nuxt-layer-web-base`.
- **`tm-shared/`**: Shared core layers, TypeScript contracts, customer layers, and UI components.

## Nuxt 4 Directory Structure & Path Aliases Standard

According to official Nuxt 4 documentation (https://nuxt.com/docs/4.x/api/nuxt-config), frontend code in Nuxt 4 apps is separated into the `app/` directory (`srcDir`):

| Alias / Prefix | Target in Nuxt 4 | Proper Usage & Scope |
| :--- | :--- | :--- |
| `~/` or `@/` | `<rootDir>/app` (`srcDir`) | Internal frontend application files (components, composables, pages, layouts, assets, app-only utils/types). |
| `~~/` or `@@/` | `<rootDir>` (Root Project) | Files located at project root outside `app/` (e.g. `~~/config/...`, `~~/scripts/...`, `~~/layers/...`). Never use `~~/app/...`. |
| `#shared/` | `<rootDir>/shared` | Code, utilities, constants, and TypeScript types shared across BOTH App (Frontend) and Nitro Server (Backend) (e.g. `#shared/types/...`, `#shared/utils/...`). |
| `#server/` | `<rootDir>/server` | Internal Nitro Server files (services, modules, database, server-only utils/types). For use within `server/`. |
| `#imports`, `#app`, `#build` | `<rootDir>/.nuxt/...` | Virtual modules and system files automatically generated by Nuxt during build. |

### Strict Architectural Boundaries

1. **NEVER use `~/server/...` or `@/server/...`**: Since `~/` points to `<rootDir>/app`, `~/server` will look inside `app/server`, which is incorrect.
2. **Frontend (`app/`) MUST NEVER import from `server/`**: Never use `import ... from '~~/server/...'`, `from '#server/...'`, or relative paths into `server/` from any file inside `app/`. Client code must never bundle or depend on server modules.
3. **Server (`server/`) MUST NEVER import from `app/`**: Never use `import ... from '~~/app/...'` or `from '~/...'` inside `server/`. If code or types are needed by both frontend and backend, extract them to `shared/`.
4. **Shared Code Placement (`#shared/`)**: Any interface, DTO, enum, validator schema, or helper function shared between client and server MUST reside in `<rootDir>/shared/` (e.g., `shared/types/`, `shared/utils/`) and be imported via `#shared/...`. Do NOT use fragile relative traversals like `../../shared` or `~/../shared`.
5. **Server Internal Alias Discipline (`#server/`)**: Within `server/` (including `server/api/`, `server/routes/`, `server/middleware/`, `server/modules/`), ALWAYS use the `#server/` alias (e.g. `#server/modules/...`, `#server/utils/...`, `#server/config`) instead of multi-level relative traversals (`../../../../`).
6. **Type Placement Discipline**:
   - App-only types: `app/types/` (import via `~/types/...` or auto-import).
   - Server-only types: `server/types/` (import via `#server/types/...` or relative within `server/`).
   - Shared types: `shared/types/` (import via `#shared/types/...`).
   - There is NO root-level `types/` folder.
7. **Project Root References (`~~/`)**: Use `~~/` or `@@/` ONLY for files truly at the project root outside `app/` and `server/` (e.g. `~~/scripts/...`). Never use `~~/app/...` (use `~/...` instead).

## Customer Builds & Validation

- **Canonical customer source:** `tm-shared/customer-layers/registry/customers.ts` (customerId, tenantId, companyName, appId, layerPath, requiredAssets, domains). Never hardcode customer identity in host apps or base layers.
- **Layer precedence (first wins):** host app → customer layer → `{cms,web}-base` → `api-base` → `config-base` → `core-base`. Host apps must not contain `app/pages` or `app/layouts`.
- **Build identity:** `TM_CUSTOMER_ID` is required for every build. Vercel builds fail closed when it is missing. It selects a customer; it is not authorization.
- **Branding/content ownership:** titles, theme colors, favicons, manifests, OG images, and customer copy live only in that customer's layer. Base layers must stay customer-agnostic.
- **Before claiming a build works, run:** `pnpm validate:registry`, `pnpm verify:scaffold`, `pnpm test:layers`, `pnpm test:hub`, `pnpm --dir tm-shared run typecheck`, `pnpm typecheck`, `pnpm lint`, plus the per-app `pnpm validate:build:cms` / `pnpm validate:build:web` and the actual build with `TM_CUSTOMER_ID` set. Do not use `| tail` when capturing gate results.
- **Hub identity:** `useHub` lives in `api-base` and is shared by both hosts; CMS auth UI (`/login`, global auth middleware) lives in `cms-base`. The CMS talks to TM Hub only through the Nitro BFF (`/api/auth/*`, `/api/hub/[...path]`); access/refresh tokens live in HttpOnly `tm_access_token`/`tm_refresh_token` cookies and never reach client JS.
- **Hub env:** `TM_HUB_URL` (https in production), `TM_AUTH_MODE=hub` (`mock` is local-only and rejected on Vercel), and `TM_CMS_APP_ID`/`TM_WEB_APP_ID` (optional overrides; defaults come from the customer registry). Probe connectivity with `pnpm hub:check`.
- **Hub provisioning:** registry app ids (`app_<customer>_cms/web`) are provisioned from the TM Hub repo with `pnpm seed:websites` (tenants, sites, apps, root/admin roles, `<customer>-root/admin@example.com`). Seeded passwords are sample values from `tm-hub/scripts/seed/shared.ts` — rotate them before real use.
